# v0.3 真实 Peer Relay dogfood

[English version](v0.3-peer-relay-dogfood.md)

本手册用于在真实 Linux Peer Relay 上验证一个来自 `main` 的不可变 v0.3
候选产物。它是人工运维流程，不是自动测试；没有维护窗口和所有测试客户端的控制权时，
不要执行任何 restart 或流量步骤。

## 被动与隐私边界

- 只使用普通 HTTP 或 iperf 应用流量。
- 不运行 `tailscale ping`，不抓包，不修改 ACL、Grants、Peer Relay policy，
  不屏蔽 UDP，也不调用 LocalAPI 的配置或 mutation 接口。
- 人工可以在受控客户端已有的网络接入之间切换，以产生自然路径变化。如果 Tailscale
  没有选择 Peer Relay，就记录为“未覆盖”，不能通过 policy 或防火墙强制实现。
- 所有保留证据只使用匿名角色：`S`（server）、`R`（relay）、`O1/O2`
  （有 collector 的 endpoint）和 `P1/P2`（没有 collector 的被动 endpoint）。
- raw topology 和角色映射只放在仓库外 mode 0700 的临时目录；接受脱敏 ledger 后删除。

## 候选与角色

只有当全部 v0.3 PR 已进入 `main`、对应 main CI 成功、并发布
`edge-<full-sha>` image 和同一次 CI 的 native collector archives/checksum 后，
才能开始。不能使用 branch build 或可变 `edge` 指针。

需要以下角色：保留 named volume 的 Compose server `S`；运行已测试 Tailscale
版本且已由控制面配置好的 Linux Peer Relay `R`；两个可观测 endpoint `O1/O2`；
两个无 Tailpath collector 的被动 endpoint `P1/P2`。本流程不创建或修改 relay 配置。

建立私有证据目录并绑定候选：

```sh
export CANDIDATE_SHA=<完整-main-commit-sha>
export MAIN_RUN_ID=<成功-main-ci-run-id>
export EVIDENCE_DIR="$(mktemp -d /tmp/tailpath-relay-dogfood.XXXXXX)"
chmod 0700 "$EVIDENCE_DIR"
gh run view "$MAIN_RUN_ID" --json headSha,conclusion \
  | jq -e --arg sha "$CANDIDATE_SHA" '.headSha == $sha and .conclusion == "success"'
gh run download "$MAIN_RUN_ID" --name native-collector-archives \
  --dir "$EVIDENCE_DIR/archives"
(cd "$EVIDENCE_DIR/archives" && sha256sum -c checksums.txt)
docker buildx imagetools inspect \
  "ghcr.io/ghostflying/tailpath:edge-$CANDIDATE_SHA"
```

最终 ledger 只记录 commit、CI URL、image digest、archive 名称/checksum、架构、
发行版和 Tailscale 版本。digest/checksum 不一致必须重新选候选。

## Preflight 与升级顺序

1. 确认全部角色归测试者控制，不会把无关流量误认为测试流量。
2. 通过独立渠道确认 `R` 的 SSH host key，禁止绕过 host-key checking。
3. 在 `R` 解压完全匹配的 archive，只运行一次被动检查并立即脱敏：

   ```sh
   ./tailpath collector --check --relay-telemetry=auto \
     | scripts/sanitize-relay-dogfood.sh collector-check \
     > "$EVIDENCE_DIR/relay-check.json"
   ```

   必须得到 `relayCapability=enabled`、`relayEnabled=true`；session 数量可以为 0。
4. 记录当前 server image 和 root-only relay collector binary rollback 副本；确认 named
   volume 同时包含 SQLite 与 `tsnet/`。绝不能使用 `docker compose down -v`。
5. **先升级 server**：固定 `edge-$CANDIDATE_SHA`，只 recreate server，验证 health、
   version、tsnet identity、History，以及旧 `O1/O2` collector 仍可上报。

   ```sh
   export TAILPATH_VERSION="edge-$CANDIDATE_SHA"
   docker compose pull server
   docker compose up -d --no-deps server
   docker compose ps server
   ```

6. **再升级 `R` collector**：安装同一 CI run 的 archive；installer 会保留已有配置，
   因此明确确认 root-only 配置仍含原 server URL 和
   `TAILPATH_RELAY_TELEMETRY="auto"`，然后只 restart collector。

   ```sh
   sudo ./install.sh --server-url <现有-tailnet-server-url>
   sudo systemctl restart tailpath-collector.service
   sudo systemctl is-active tailpath-collector.service
   ```

## 脱敏证据

从已授权 Tailnet 节点读取 topology 到私有目录，用私有角色映射找到目标 logical edge
ID，再通过 sanitizer 输出证据；edge ID 本身不会进入输出：

```sh
chmod 0600 "$EVIDENCE_DIR/roles.json"
curl --fail --silent http://<server-tailnet-name>:8080/api/v1/topology \
  > "$EVIDENCE_DIR/topology.raw.json"
scripts/sanitize-relay-dogfood.sh topology <scenario> <private-edge-id> \
  < "$EVIDENCE_DIR/topology.raw.json" \
  > "$EVIDENCE_DIR/<scenario>.json"
```

sanitizer 只保留 path/state、两个方向是否有流量、relay/VNI 是否存在、provenance
数量、identity status 集合与 clock-skew 布尔值。不能保留 node、relay、observer、
session 或 endpoint ID。raw UI 截图不能作为证据；如确需截图，必须在仓库外完成脱敏并
逐项检查。

## 测试矩阵

每个场景之间停止应用流量，等待上一条 edge aging 后再切换角色：

| 场景 | 普通应用流量 | 期望 |
| --- | --- | --- |
| `two-observable` | `O1` 与 `O2` 经 `R` 双向通信 | 仅一条 Peer Relay logical edge；endpoint 与 relay provenance 同时存在但流量不相加 |
| `one-observable` | `O1` 与 `P1` 经 `R` 双向通信 | 仅一条 Peer Relay edge；一个 endpoint observer 加 relay provenance |
| `no-collector` | `P1` 与 `P2` 经 `R` 双向通信 | 只靠 relay provenance 形成一条 edge；identity 可 resolved/partial/anonymous，但不能猜测 |

每个场景检查 Live 方向/速率、显式 relay anatomy、VNI、identity status、observer
数量和 History transition。出现 Unknown/Anonymous 是诚实结果；错误合并或生成
relay-to-client business edge 是 blocker。

## Direct → Peer Relay → Direct

1. 客户端自然 Direct 时产生普通双向流量并保存脱敏 `path=direct` 证据。
2. 停止流量；人工把一个受控客户端切到另一个已有网络接入，使 Tailnet 自然选择已配置
   的 `R`。
3. 恢复同一应用流量，必须只出现一条带 relay provenance 的 `path=peer_relay` edge。
4. 停止流量，恢复原网络，再次产生流量，必须回到 `path=direct`。
5. History 必须按 receive time 记录 Direct、Peer Relay、Direct。

如果需要 Tailpath probe、防火墙 fault 或控制面 policy 变化才能实现，停止并记录未覆盖。

## Restart 门禁

逐项执行，每项都必须有 rollback：

1. 停止应用流量后 restart `R` collector。首个 relay sample 只能作为 baseline；恢复流量后
   只统计新 delta，并且日志只有一次 recovery transition。
2. 停止流量后 restart `R` 的 `tailscaled`，即真实 relay data source。恢复后再次产生
   流量，canonical edge 不变且无 catch-up bytes。
3. 只 restart `S`。tsnet identity/named volume 不变，Live topology 与 History 恢复，
   collector full resync 不补报离线流量。

任何 identity split、伪造 catch-up、History 丢失、endpoint 泄漏或无界 retry 都是
blocker。

## 结束与 rollback

redacted ledger 对每个场景和 restart 标记 pass/fail/not-exercised。使用所有已知名称、
suffix、地址、stable ID、session ID、endpoint 与 credential 对保留文件做最终扫描，然后
删除 raw topology、角色映射和 raw logs。

全部通过前保留旧 server image 和 relay collector binary。rollback 时固定到已记录的旧
image，只 recreate server；恢复 root-only collector 副本、reload systemd 并只 restart
collector。未经明确兼容性审查不要 rollback 数据库 migration；v0.3 不提供受支持的
backup/restore contract。
