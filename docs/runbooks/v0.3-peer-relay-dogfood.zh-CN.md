# v0.3 Peer Relay 容器 dogfood

[English version](v0.3-peer-relay-dogfood.md)

本手册使用一次性容器 Tailnet 验证真实的 Tailscale 控制面、WireGuard、Peer Relay、
LocalAPI 和应用流量，不要求也不修改长期运行的 Relay 主机。

## 边界

- 只产生普通 HTTP 应用流量；不运行 `tailscale ping`、不抓包，Tailpath 不调用 LocalAPI
  mutation 路由。
- harness 只能在一次性容器内启用 Peer Relay 和修改防火墙；它不直接编辑宿主机防火墙、
  ACL、Grants 或其他 Tailnet 节点，但 Docker 创建和删除一次性 bridge network 时可能
  管理宿主机 netfilter。
- relay 模式只在 endpoint namespace 放行 DNS、到 Tailpath server 的 direct UDP 和
  Relay UDP 端口，从而隔离业务路径而不把 collector 上报路径也强制变成 Relay。
- raw topology、node identity、地址、endpoint 和 session ID 只能存在于仓库外 mode
  0700 目录；仓库只保留 sanitizer 输出。
- reusable auth key 只写入 mode 0600 临时文件；所有节点 enrollment 后、业务流量前，
  `up` 会立即清零原文件和 Compose 副本。

## Tailnet 前置条件

使用专用 Tailnet 或专用 ephemeral tag。控制面 policy 必须允许测试节点使用测试 Relay：

```json
{
  "src": ["tag:tailpath-smoke"],
  "dst": ["tag:tailpath-smoke"],
  "app": {
    "tailscale.com/cap/relay": []
  }
}
```

只有 `R` 容器会启用 relay server；范围同样严格的其他 Grant 也可以。

## 候选门禁

最终测试必须绑定一次成功的 `main` workflow，同时发布 `edge-<full-sha>` 和匹配的
native archives。开始前记录 workflow URL、image digest、archive 和 checksums。
可变 `edge`、branch tag 或短 SHA 都不能作为最终候选。

如果 GHCR 需要认证，先把 Docker credential 隔离到临时目录，再交互式写入
ephemeral key：

```sh
export CANDIDATE_SHA=<40-character-main-sha>
export TAILPATH_VERSION="edge-$CANDIDATE_SHA"
export DOCKER_CONFIG="$(mktemp -d /tmp/tailpath-docker-config.XXXXXX)"
chmod 0700 "$DOCKER_CONFIG"
gh auth token | docker login ghcr.io -u "$(gh api user --jq .login)" --password-stdin

install -m 600 /dev/null /tmp/tailpath-smoke-authkey
IFS= read -r -s AUTH_KEY
printf '%s\n' "$AUTH_KEY" > /tmp/tailpath-smoke-authkey
unset AUTH_KEY
```

开发 harness 时可以不设置 `TAILPATH_VERSION`，此时 `up` 构建本地
`smoke-<branch-sha>`；这种运行不能满足最终 artifact 门禁。

## Server-first 混合版本窗口

在完整候选矩阵之前，先使用 immutable candidate server 和上一个正式版本的
ordinary collector。Peer Relay telemetry 是 v0.3 新能力，因此 relay collector
仍使用 candidate：

```sh
export TAILPATH_SMOKE_ORDINARY_COLLECTOR_VERSION=0.2.0
scripts/smoke.sh up
scripts/smoke.sh status
```

server 输出的版本必须是 `edge-$CANDIDATE_SHA`，ordinary collector 版本必须是
`0.2.0`。记录 observer A 的第一次 `lastSeen`，在没有应用流量的情况下等待超过
两个配置的 heartbeat interval，然后要求 `lastSeen` 已推进且 runtime 仍在线。
随后运行普通的 A 到 B HTTP 流量，要求 canonical A-B edge 出现正向流量，并且
15 分钟 History 非空。持续 resync/recovery 日志、runtime offline、report 被拒绝或
没有流量都属于 blocker。

ledger 只能保留脱敏后的布尔值、版本、经过的 heartbeat interval 数和 pass/fail。
完成该窗口后执行 `down`，重新写入 ephemeral key，取消
`TAILPATH_SMOKE_ORDINARY_COLLECTOR_VERSION`，再使用相同 immutable candidate
运行仍需执行的同版本场景。

## Topology 生命周期

启动五个 ephemeral Tailscale 节点：tsnet server `S`、Peer Relay `R` 和 endpoint
`A/B/C`。`A/B` 运行普通 collector，`R` 运行 Relay collector，`C` 没有 collector。

```sh
scripts/smoke.sh up
scripts/smoke.sh relay-check
```

`up` 拉取不可变镜像后，立即删除临时 Docker 登录：

```sh
docker logout ghcr.io
find "$DOCKER_CONFIG" -type f -delete
rmdir "$DOCKER_CONFIG"
unset DOCKER_CONFIG
```

`relay-check` 必须显示 `relayCapability=enabled` 和 `relayEnabled=true`，session 数可以为
0。继续之前确认两个 key 文件都已为 0 字节。若 enrollment 或 capability detection
失败，应直接执行 `down`，不能由 harness 放宽测试或修改 policy。

## Direct 基线

```sh
scripts/smoke.sh traffic a b
scripts/smoke.sh path a b
```

传输期间被动 path 必须为 `direct`。Topology 只应有一条 active `A-B` 业务 edge，
双向流量为正并包含两个 endpoint observations。

## Peer Relay 切换

停止业务流量，仅隔离 endpoint UDP，再恢复相同 HTTP transfer：

```sh
scripts/smoke.sh udp relay a b
scripts/smoke.sh traffic a b
scripts/smoke.sh path a b
```

path 必须变为 `peer_relay`。`A-B` edge 必须包含 Relay identity、VNI、双向正流量、
两个 endpoint observations 和一个 relay-session observation，且流量不能重复相加。

如果 collector 到 server 的控制路径本身使用 Peer Relay，R 也会把它当成真实 session
观测。harness 特意保持 `A-S`、`B-S` 为 Direct，使业务断言不歧义；这不代表自然部署中
这些控制 session 不属于流量。

## Provenance 矩阵

每次停止 collector 后等待 endpoint evidence 超时，再通过现有 Relay path 产生新流量：

| 场景 | Collectors | 期望 `A-B` provenance |
| --- | --- | --- |
| `two-observable` | `A`、`B`、`R` | 3 observations，1 relay session |
| `one-observable` | `A`、`R` | 2 observations，1 relay session |
| `no-collector` | `R` | 仅 1 relay-session observation |

```sh
scripts/smoke.sh collector stop b
# 等待超过 server evidence window，再执行 a -> b transfer
scripts/smoke.sh collector stop a
# 再次等待并执行 a -> b transfer
```

Relay-only 流量仍必须保留方向，不能生成 relay-to-client 业务 edge。resolved、partial、
anonymous identity 都是诚实结果；错误 identity merge 是 blocker。

## Restart 门禁

每次 restart 前停止业务流量：

```sh
scripts/smoke.sh collector restart r
scripts/smoke.sh restart-relay
scripts/smoke.sh restart-server
```

- Relay collector restart 后先建立 counter baseline，恢复流量后只能上报新 bytes。
- `restart-relay` 重启 Relay 容器，再把 collector sidecar attach 到 Docker 新建的 network
  namespace。控制面 Relay 状态收敛期间客户端可以短暂回退到 DERP 或 unknown；最多被动
  检查 90 秒，确认 `peer_relay` 恢复后才能新建 workload connection。canonical
  business edge 必须稳定，不能产生 catch-up spike。
- server restart 必须保留 tsnet identity、named volume、Live topology 和 History。

## 恢复 Direct 与 History

```sh
scripts/smoke.sh udp restore a b
scripts/smoke.sh collector start a
scripts/smoke.sh collector start b
scripts/smoke.sh traffic a b
scripts/smoke.sh path a b
```

当前 path 必须回到 `direct`。同一 canonical edge 的 History detail 必须按顺序包含：

```text
direct -> peer_relay -> direct
```

restart recovery 或新旧 provenance 竞争产生的其他真实 transition 必须继续显示，不能为了
得到三条事件而从 History 改写删除。

relay underlay privacy gate 需要停止 endpoint collectors、等待其 evidence 过期，再让
`A` 与没有 collector 的 passive endpoint `C` 产生 relay-only 流量；这个数据库中 `C`
不得提供过普通 Direct observation。把 SQLite、WAL、SHM 复制到私有 evidence 目录，并
扫描三者中是否出现 `C` 的一次性 underlay 地址，任何命中都是 blocker。不能用 `A` 或
`B` 做这个 canary：普通 Direct endpoint 按设计允许持久化，会让测试口径产生歧义。

## 证据与清理

从 raw topology 私下选择业务 edge ID，再通过 fail-closed sanitizer：

```sh
scripts/sanitize-relay-dogfood.sh topology <scenario> <private-edge-id> \
  < topology.raw.json > scenario.json
```

保留的 ledger 只能记录 candidate SHA/workflow/digest、Tailscale 与容器架构、pass/fail、
path/state、双向正流量布尔值、Relay/VNI presence、provenance 数量、identity status 类别和
clock-skew 状态。

最后必须执行：

```sh
scripts/smoke.sh down
```

`down` 会 logout 一次性节点，只删除 `tailpath-smoke` project 的容器与 volumes，清零并
删除 staged credentials 和 runtime 文件。最终运行结束后 revoke reusable key。
